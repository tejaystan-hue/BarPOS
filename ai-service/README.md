# BarPOS shared tablet and optional AI service

Use Node.js 22.16 or newer. No additional packages are required. Render runs node server.mjs with HOST=0.0.0.0, its assigned PORT and managed HTTPS. BARPOS_DEVICE_TOKEN must contain at least 24 characters. The existing paid BarPOS service uses the approved 1 GB disk mounted at /var/data. The shared SQLite database lives at /var/data/barpos-shared.sqlite; there is deliberately no ephemeral fallback. Missing persistent storage returns 503 for shared routes. The optional blueprint does not provision a disk; configure the approved disk on the existing service.

All /shared/* routes require the device Bearer token. Manager login additionally checks an active four-digit manager PIN and issues an eight-hour in-memory session, required for snapshots and manager edits. Restarting the service ends manager sessions; public tablets reconnect automatically. /shared/public provides sale buttons, drawer-open state and kitchen-only tickets without prices, employee records or inventory/cost reports. /shared/clock checks the actual employee PIN. /shared/checkout records cash, ingredients, journal, drawer and kitchen ticket atomically with a unique checkout key. Kitchen updates check the expected current status. Manager edits use revision checks to reject overwriting a concurrent sale or another tablet's edit. Pairing imports current records only when the shared database is empty; later tablets authenticate and download those records.

This is an online trial. Five identical tablet interfaces use REGISTER, KITCHEN, CLOCK IN / OUT and manager-only screens. An unconfirmed checkout is persisted on the originating tablet and retried with the same key; it must be recovered before a new cash sale. Manager saves also retain their request for reconciliation if the acknowledgement is lost. Count-entry drafts stay local. Manager backups include shared business records and PINs; keep them private and off the tablet. Connected tablets cannot restore a local backup over live shared records. Daily manager backups are still needed. A disk is durable storage, not proof of tested disaster recovery.

Shared requests are capped at 15 MB and 600/minute per socket address; PIN routes are capped at 30/minute. This address can be shared behind a proxy. Shared operations do not call OpenAI or consume AI allowance. Photo/holiday/menu help uses OPENAI_API_KEY and OPENAI_MODEL on the server, two concurrent requests and 30/hour per socket address. AI requests accept one JPEG photo, up to 200 inventory items and bounded history. Responses require human review; no automatic ordering or silent menu/stock edits. An AI configuration check is not a live provider test. The tablet uses the device token, never the OpenAI key. Do not commit .env, customer records, database files or secrets.

/live is a public liveness check. /health, /assist and shared routes require authorization. For local development use node --env-file=.env server.mjs; defaults are HOST=127.0.0.1 and PORT=8787. Tablet connections require HTTPS. Public menu/kitchen caches and saved PDFs remain viewable offline, but connected sales, employee punches and manager changes require the server.

Run node --test server.test.mjs shared.test.mjs. Tests use synthetic data and simulated provider responses. They verify authentication, atomic stock/cash updates, retry deduplication, conflicting edits, kitchen/clock rules and file persistence. They make no live OpenAI calls and do not measure photo accuracy.

AI follows the official [image input](https://developers.openai.com/api/docs/guides/images-vision) and [structured output](https://developers.openai.com/api/docs/guides/structured-outputs) APIs. The service requests store:false, which does not assert that the provider has no other retention rules. Photos and request bodies are not deliberately logged.

Build 13 adds version 10 snapshots, named drawer groups and manager-controlled tablet assignments. Existing cash history migrates to Main bar drawer. Multiple registers can share a group; separate groups have independent cash periods and closing totals. /shared/register registers a device under manager authorization; public metadata allows each register to display its assignment. Checkout rejects a stale assignment and preserves idempotent committed receipts. The app reconnects automatically after one-time MANAGER → Settings → Tablet connection pairing. Hardware drawer opening is not included.

Build 20 uses version 12 snapshots, with nullable cash-period opener IDs for public-register openings. Existing employees, cash history and assignments migrate intact. Checkout can atomically start its assigned period with explicit opening_cash (integer cents), without a manager session. Failed orders roll back the opening; retries and multiple registers never add starting cash twice. The first successful checkout chooses the starting balance. Older manager snapshot writes are rejected until tablets update, preventing older clients from restoring the previous opening constraint. Existing backups 9–11 can still initialize the service. Hardware opening still requires a configured compatible printer/drawer.
